= Why does git suck?
:description: English intuition vs Git's vocabulary — commit/push/add are the wrong words — plus a map into worktree essays and mailed UX critiques.
:revdate: 2026-09-25
:keywords: blog, git, UX, naming, gitu, worktrees

Git's command names feel wrong because they are wrong for English-native intuition — and because the product never treated that mismatch as a first-class bug.

This is an overview essay. It opens on vocabulary, then branches into tighter pieces on worktrees and into a stack of critiques I have already mailed to git@vger.kernel.org. Read the worktree pair next if placement is what is burning you today.

== The feely English goop

Linus and Junio are not native English speakers. That is not a gotcha biography line; it is a design constraint you can still see in the CLI.

Commands lack correct nuance. Terms overlap. The vocabulary asks you to accept a private jargon that only sometimes rhymes with ordinary English — then gaslights you when your first guess matches the dictionary and not the man page.

That goopy, ambiguous mess is not "steep learning curve" mystique. It is naming debt.

== Commit, push, add — the words that should have been

**`git commit`** should be what **`git push`** is.

You *commit* changes from your computer to an official record. When you commit a crime, you take personal thoughts and make them part of the world. Your computer is not the world; it is local thoughts and workspace before they are publicized.

In publishing terms, that outward act is closer to **publish**. If the move is specifically local → public hosting service, **upload** is the sharper word. Today's `git commit` should have been **`git save`** — the common meaning of saving a file. A local record is not official.

**`git add`** should have been **`git stage`**.

"Add" sounds like adding to existing history. To add, you have to have something; an empty stage is not something you add *to*. "I'm going to add a prop to the stage" is inaccurate — you put or move a prop onto the stage.

Add's nuance: something need not have existed, or separate entities cease to be separate (cooking: add sauce to the dish, A+B becomes the dish). Indexing existing work is not changing identity through composition. Staging is.

If your fingers still type `git commit` and `git add`, fine — the muscle memory is the ecosystem. The point is the *mental model* Git sold you is lying about English, and that lie costs newcomers and agents alike.

== gitu / git-un / git-unfuckified

I forked Git to experiment with a clearer CLI face.

Historically the fork branding is **git-unfuckified**, with a `gitu` front-end that remaps the verbs. The tree has also been referred to as **git-un**. Same project intent; do not treat the names as three unrelated products.

Rough `gitu` map (from the fork):

[cols="1,1,2", options="header"]
|===
| gitu | git today | Intent

| `save`
| `commit`
| Local snapshot with a message

| `stage` / `unstage`
| `add` / `reset HEAD --`
| Move work onto / off the stage

| `upload`
| `push`
| Local → remote hosting

| `download`
| `pull`
| Remote → local

| `history`
| `log --oneline`
| Read the record

| `discard` / `undo`
| checkout / soft reset helpers
| Back out without thesaurus gymnastics
|===

Aliases do not absolve upstream naming. They prove the rename map is teachable.
